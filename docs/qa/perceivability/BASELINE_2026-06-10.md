## Capture protocol notes (for repeat passes)

- No HTML `<audio>` element: the prototype uses the Web-Audio buffer manager. Seek via `await window.SonoitePrototype.audio.seekTo(t)` + 2.5 s settle; read time via `audio.getCurrentTime()`. Seeks verified accurate (±2.5 s drift from settle wait).
- **CRITICAL (discovered during Pass 1a): `audio.seekTo()` alone does NOT move the room.** The update loop's time is wall-clock anchored (`state.currentTime = performance.now()/1000 - transportStartSeconds`, `experience.js` update loop), so a programmatic audio seek leaves the room's phase behind (observed: audio at 276 s / room at 8.5 s). A valid test seek must sync both clocks:
  ```javascript
  await p.audio.seekTo(t);
  p.state.currentTime = t;
  p.transportStartSeconds = performance.now() / 1000 - t;
  ```
  The UI transport does this internally; only programmatic seeks bypass it. This is the prototype incarnation of the repo's known seek-desync — and a latent runtime bug (room time = wall time, so any audio stall drifts room vs. sound). Logged for a later hardening pass, not fixed in Pass 1.
- Experience handle: `window.SonoitePrototype`. Phase: `p.getMacroState(t).phase`.
